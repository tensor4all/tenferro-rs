# The cubecl fork: what it carries, what stays upstream, and the own-backend contingency (#1945)

Decision record for the `tensor4all/cubecl` fork that `tenferro-rs` pins, written after the held-CUDA
session (#2059), the owning pending transfers (#2073, #2076) and the source publication (#2101) were
delivered against it.

## 1. What the pin is

| Item | Value |
| --- | --- |
| Fork | `tensor4all/cubecl`, `main` at `1811309791f675125379b326bf748f2ec1e29f2a` |
| Upstream | `tracel-ai/cubecl`, whose `main` (`4362f783f`) is 388 commits ahead of the fork's merge base |
| Fork-only commits | 62 |
| Version line | releases `v0.10.1`, `v0.10.2` of the fork's packages |
| Downstream pin | `cubek` fork release branch `release/t4a-0.2.2` (`507c91f5a`), which carries one cubecl revision |

The fork is therefore **not** a thin overlay of the #1945 work. It is the release fork that this
workspace's CUDA stack builds on, and it already carried, before #1945: CUDA OOM reclaim, complex-plane
warp reduction, exact wgpu submission completion, device-service wakeups, host-visible primary
allocation, removal of redundant upload copies in `ComputeClient::create*`, a read-only loaded-kernel-id
diagnostic, and the release/CI plumbing that keeps those packages publishable.

## 2. What #1945 added to it, and why each is needed here

| Change | Fork PR | Why `tenferro-rs` needs it |
| --- | --- | --- |
| `ComputeServer::check_errors` / `Client::check_errors`: report producer errors and dispatch the host queue without rotating the drop queue | #27 | The held session's publication boundary must surface backend errors without a `flush`, which would wait for the previous fence. `download_pending` / `upload_pending` / `publish` all publish through it. |
| CUDA write path evaluates the staging policy | #28 | `Command::write_to_gpu` queued staged host bytes but only the kernel path checked `drop_queue.should_flush()`. With a publication boundary that no longer flushes, a write-only workload never reached the default 64-allocation / 64 MiB thresholds and retained staged bytes indefinitely. |
| `ComputeServer::write` is `unsafe fn` with a write-authority contract | #29 | A safe server write accepted a lifetime-free binding, so a borrowed value could be written through a binding derived from the borrow. `Session::tensor_binding` and `Session::array_arg` are `unsafe` on our side (#2093); this is the substrate half of the same contract. |

## 3. The residue, and why the fork will not carry it

The remaining hole is cubecl's **checked kernel launch**: the launcher generated by `#[cube(launch)]` is a
safe function whose arguments include writable tensor bindings, and `launch_unchecked` — which is
`unsafe` — is required only for arguments the launcher cannot check, not for write authority. A user
holding a lifetime-free `TensorBinding` can therefore launch a kernel that writes storage an outstanding
borrow still reads, from safe code, inside cubecl itself.

`tenferro-rs` does not carry a fix for this, for three reasons:

1. **We cannot reach it.** Our layer never hands out a cubecl handle, binding or client, and the
   accessors that derive a binding from a borrow are `unsafe` with the write-authority contract (#2093).
   Making the launch safe-again-unsafe changes nothing about what our own code can do.
2. **It is cubecl's API decision, not a defect with one obvious fix.** Marking every writable launch
   `unsafe`, or introducing a separate write-authority binding type, changes the ergonomics of every
   cubecl kernel in every downstream project. That decision belongs to the upstream maintainers, who can
   weigh it against their whole surface; a fork-only version would diverge from them for no local gain.
3. **The fork's cost is real.** It already diverges 62 commits from upstream. Carrying an unbounded API
   redesign on top of that increases the rebase and review surface of every future pin bump, which is the
   opposite of what the fork exists for.

What we owe upstream instead: a focused proposal that names the hole, the two candidate shapes, and the
fact that `crates/tenferro-linalg` and the samples would have to annotate their launch sites (18 sites in
`gpu/linalg.rs` plus the QR variants and the extension samples) if launches became `unsafe`. That is a
proposal to `tracel-ai/cubecl`, not a fork commit.

## 4. When the fork goes away

The fork is retired when either holds:

1. **Upstream absorbs the changes we need.** The soundness-relevant set is #27, #28 and #29; the rest are
   release-fork conveniences that upstream either has or does not want. Upstream `main` is 388 commits
   ahead, so any proposal is a rebase onto current upstream, not a cherry-pick of our history.
2. **We migrate to an owned backend** (§5), at which point the pin disappears with the backend.

Until then the pin stays, and every bump re-runs the CUDA test partition and the held-session /
pending-transfer / publication tests against the new revision.

## 5. Own-backend contingency inventory

If the fork ever becomes untenable — upstream rejects the soundness changes, or the divergence cost
exceeds maintaining a backend — the replacement surface is bounded and identifiable:

| Surface | Where it lives now | Replacement cost |
| --- | --- | --- |
| Kernel JIT, fusion codegen, launch plumbing | cubecl-core / cubecl-macros / cubecl-runtime, used across `tenferro-gpu` (60 files) and `tenferro-linalg`'s GPU kernels (84 files workspace-wide mention cubecl) | Largest item: a codegen path plus a launch API, including the checked-launch hole above |
| Device memory pool, staging and its retirement bound | cubecl-runtime / cubecl-cuda (`reserve_cpu`, drop queue, flushing policy) | Moderate: our own pool already owns retirement (`TransferRetirementQueue`, workspace retirement); the *allocation* pool and staging bound would move in |
| Streams, events, stream slotting, event domains | cubecl-runtime / cubecl-cuda (`StreamId`, `drop_queue`, event domain ids) | Moderate: our runtime already identifies streams, events and domains by captured logical ids |
| Graph/execution-engine contract, compiled-kernel cache | cubecl-runtime (`KernelId`, memory management, scheduler) | Bounded: our runtime and plan cache already own the tenferro-side contracts |
| cudarc / driver bindings | cudarc directly in `tenferro-gpu` (FFI, cuBLAS, cuSOLVER, events, pinned host memory) | Already ours; unaffected by the fork |
| Extension/sample API | our `unsafe` bindings plus `samples/cubecl-kernel` | Small: it is our surface already |

The migration is a backend swap behind our own types, which is why every contract added for #1945 —
held sessions, pending transfers, publications — deliberately mentions no cubecl type in its public API.
No public `tenferro-rs` API breaks if the pin is replaced.

## 6. What this record does not claim

- It does not claim the fork is unsound for our use, or that upstream requires the soundness changes: it
  records that our layer cannot reach the residue and that the fix is upstream's call.
- It does not claim the fork's 62 commits are all upstreamable or all ours; the inventory above lists what
  the fork provides, and only #27/#28/#29 are proposal candidates.
- It does not schedule the own-backend migration. The inventory exists so the contingency is priced
  before it is needed, not to start it.
