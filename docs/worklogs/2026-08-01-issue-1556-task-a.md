# Worklog: #1556 Phase 0 Task A — Runtime Endpoint Key

## Scope

Task A establishes the runtime control-plane transfer key as the immutable
`TransferEndpoint` value `(EngineId, StorageClass)`. It does not change storage
ownership, allocation domains, provider-device identity, event-domain
implementation, or backend behavior.

## Context Read

- Repository and shared Tensor4all rules, including public-surface, structured
  error, transactional snapshot, performance, documentation, and test rules.
- Accepted [Issue #1556](https://github.com/tensor4all/tenferro-rs/issues/1556)
  and its Phase 0 architecture amendment.
- The Phase 0 plan and the storage-ownership design boundary.
- Runtime policy, transfer, snapshot, preparation, schedule, execution, and
  existing transfer integration/unit tests.

## Decisions

- `TransferEndpoint` has private fields, value-based derived equality,
  ordering, and hashing, with public constructor/accessors and runnable
  examples.
- Candidate, frozen snapshot, preparation reachability, schedule, and
  execution provider maps all use endpoint pairs. `ExecutionLocation` stores
  the canonical endpoint and keeps `EventDomainId` as execution metadata.
- Candidate validation checks both endpoints against the complete engine
  candidate before identity allocation or snapshot publication. The same
  validation runs before reconfiguration publication, so invalid routes cannot
  leave partial runtime state.
- Same-`Arc` registration remains idempotent. A different provider returns a
  `ConflictingRegistration` containing both endpoint values. Missing-route
  preparation and execution diagnostics identify both endpoints; event domains
  remain additional execution diagnostics only.
- Transfer request storage-class accessors and provider contract validation
  remain unchanged because they describe the tensor contract, not route-key
  identity.

The storage-class-only registration and lookup path was removed rather than
retained through aliases or wrappers.
