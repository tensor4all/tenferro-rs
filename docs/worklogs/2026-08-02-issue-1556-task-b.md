# Worklog: #1556 Phase 0 Task B — CUDA Engine Identity

## Scope

Migrate CUDA device discovery and runtime/backend selection to typed
`CudaDeviceId` values, require caller-selected `EngineId` values for canonical
CUDA engine registration, and bind provider identity from the selected device
held by the runtime/backend. This work remains in the Phase 0 control plane;
it does not add allocation, storage ownership, or lease types.

## Context read

- `AGENTS.md`, workspace `CODING_RULES.md`, `REPOSITORY_RULES.md`, and the
  current shared Tensor4all common, Rust, performance, and docs/test rules.
- CodeGraph traces for CUDA runtime/backend construction, registration,
  selection, and workspace callers.
- CUDA runtime/backend construction, CUDA runtime registration, device value
  types, runtime adapter tests, and current workspace CUDA constructor callers.
- `cudarc 0.19.8` `driver::result` wrappers already present in the worktree
  for driver initialization, device count, device lookup, and device names.

## TDD RED evidence

Added focused tests for the canonical typed constructor and registration
signatures, runtime/backend typed device accessors, caller-selected engine IDs,
two selected devices, fixed-ID helper removal, and unavailable selection
preserving the requested ID plus discovered records. The existing device fake
driver tests remain in place; the new runtime-adapter tests exercise the same
fields through the caller-selection seam.

  cuda_public_constructors_and_registration_require_typed_selection --no-fail-fast

Before adding the focused test, compilation failed with 18 errors from the

integer constructor calls. These were the expected RED API mismatches.

## Implementation and GREEN evidence

- `CudaRuntime::new` and `CudaBackend::new` now take `CudaDeviceId` and return
  `CudaDeviceError`; runtime construction calls `cuda_devices()` and the
  crate-private `select_device` seam before CUDA initialization.
- Runtime state stores and exposes the selected `CudaDeviceId`; `CudaBackend`
  exposes the same selected value through `device_id()`.
- `cuda_runtime_engine_registration` is the canonical registration function and
  takes a caller-selected `EngineId`. `cuda_runtime_engine_id` and the
  `_with_id` path/export were deleted. `tenferro-ad` explicitly owns its own
  eager-runtime engine ID at its call site.
- Provider identity is built from the selected backend device ID, and current
  callers, examples, ignored tests, guides, and design documentation use
  explicit `CudaDeviceId` values.
- The public inventory test uses filesystem reads; no new `include_str!`
  substring test was added.
