# Worklog: #1556 Phase 0 Task B — CUDA Engine Identity

## Scope

Migrate CUDA device discovery and runtime/backend selection to typed
`CudaDeviceId` values, require caller-selected `EngineId` values for canonical
CUDA engine registration, and bind provider identity from the selected device
held by the runtime/backend. This work remains in the Phase 0 control plane;

## Implementation and GREEN evidence

- `CudaRuntime::new` and `CudaBackend::new` now take `CudaDeviceId` and return
  `CudaDeviceError`. Runtime construction initializes the driver and looks up
  only the selected ordinal; full `cuda_devices()` discovery is reserved for
  the driver's invalid-device failure path.
- Runtime state stores and exposes the selected `CudaDeviceId`; `CudaBackend`
  exposes the same selected value through `device_id()`.
- `cuda_runtime_engine_registration` is the canonical registration function and
  takes a caller-selected `EngineId`. `cuda_runtime_engine_id` and the
  `_with_id` path/export were deleted. `tenferro-ad` explicitly owns its own
  eager-runtime engine ID at its call site.
- Provider identity is built from the selected backend device ID. Current
  public examples and guides discover `CudaDeviceInfo` records with
  `cuda_devices()` and select a returned ID rather than assuming ordinal zero.
- Removed CUDA API absence is covered by compiler-negative UI cases rather
  than filesystem-read substring assertions.

## Sol review follow-up

The spec review identified three important gaps in commit `a61406c8`:

1. CUDA public-absence assertions read implementation files and matched source
   substrings instead of asking the compiler to enforce the public contract.
2. The no-hardware identity test compared independently created values but did
   not flow caller-selected engine and device identity through a value consumed
   by production registration.
3. Public CUDA examples selected ordinal zero directly rather than selecting a
   discovered `CudaDeviceInfo`.

The follow-up removes the CUDA filesystem/substr assertion, adds three
feature-gated trybuild cases for the two removed exports and bare-integer
`CudaBackend::new`, and routes `cuda_runtime_engine_registration` through a
crate-private `PreparedCudaRegistrationIdentity`. The no-hardware test sends
two distinct `EngineId`/`CudaDeviceId` pairs through that exact helper and
asserts the prepared engine and provider/device fields. Public Rust examples,
the quickstart, current guides, and the CUDA backend design example now select
from `cuda_devices()`; hardware-free rustdoc checks the discovery-based helper
signature without invoking it.

## Selected-device lookup quality follow-up

The quality review found that `CudaRuntime::new` performed full CUDA discovery
before initializing the selected device. That queried every visible device
name, duplicated work proportional to device count, and allowed an unrelated
device-name failure to reject an otherwise valid selected device.

The proportional fix initializes the CUDA driver and calls
`cudarc::driver::result::device::get` for only the selected typed ordinal on the
normal path. A small classifier recognizes only
`CUresult::CUDA_ERROR_INVALID_DEVICE`; that branch calls `cuda_devices()` and
maps its records to `CudaDeviceError::Unavailable`. Other lookup failures map
to `CudaDeviceError::Initialization` with operation `get_device`. Context
retention/current-context setup and CubeCL client creation follow successful
selected-device lookup. The now-unused selection helper was replaced by the
small unavailable-error constructor used by production and existing
hardware-free field tests.

Focused RED command and observed result:

```text

failed to compile with E0432 because is_invalid_device_lookup did not exist
```
