# N-dimensional FFT over multiple axes

Issue #2364. `tenferro-fft` gained `fftn`/`ifftn`/`rfftn`/`irfftn` on the eager
`FftExecutor` and on `TracedTensorFftExt`, without a second execution path or a
second descriptor.

## Decisions

- **One descriptor, one loop.** `FftOp` now declares `axes: Vec<usize>` plus one
  optional requested length per axis; a one-axis request is that struct with a
  single axis and nothing else. `FftExecutor::fftn` builds the same `FftOp` the
  traced builder builds and calls `execute_fft_op`, which the traced/extension
  path reaches through `execute_fft_extension_reads_on_session`; the axis loop,
  the per-axis operation choice, and the plan-cache reuse therefore live only in
  `execute_fft_op` (`crates/tenferro-fft/src/lib.rs`). The backend SPI stays
  one-axis: the loop splits a request into single-axis `FftPlanSpec` values, and
  it forwards the plan store's ownership tag so a caller-owned `FftPlanCache` is
  never treated as engine-owned storage.
- **No transform arithmetic of our own.** Each axis is a `rustfft` complex plan
  or a `realfft` R2C/C2R plan call, reached through the pre-existing
  `cpu/lanes.rs` kernels and the `(length, dtype)` plan cache. The new code only
  orders axes, derives the per-axis operation
  (`FftOperation::step_operation`), and threads intermediate shapes.
- **Normalization is defined once for the whole transform.** With
  `P = prod(shape over axes)`: `Backward` scales the inverse by `1/P`, `Forward`
  scales the forward transform by `1/P`, `Ortho` scales both by `1/sqrt(P)`.
  Because per-axis factors multiply, this equals composing one-axis calls with
  the same norm, and the tests pin both that equivalence and the rejected
  alternative: applying the whole factor once per axis is off by `P^(k - 1)`
  for `k` axes, so the two-axis test sees exactly `P`.
- **Real transforms follow the NumPy convention.** The real axis is the last
  declared axis; it runs first for `rfftn` (real input) and last for `irfftn`
  (real output). `fftn` on real input keeps the full spectrum, matching the
  existing one-axis `fft` on real input.
- **One validator.** Axis normalization, duplicate/empty rejection, one length
  per axis, dtype, and concrete transform shapes are checked in
  `validated_fft_op`, which the eager executor, the traced builder, and
  `eager_ext` all use.
- **AD reused as-is.** The adjoint of an n-dimensional complex transform is the
  inverse of the same axis list with the adjoint norm, so `FftOp::c2c_adjoint`
  generalizes by construction; only the residual length restoration needed to
  iterate over axes. The AD rule was not duplicated per axis.
- `FftPlanSpec::normalized_axis`/`requested_len` are no longer `const fn` because
  the spec now holds its axes in a `Vec`. `FftPlanSpec::new` is crate-private, so
  no caller outside the crate can hold a spec in a const context; the effect is a
  source-compatibility break for in-crate const users only.
- Eager `fftn` was added to `FftExecutor` only. `TensorFftExt`,
  `TensorReadFftExt`, and `EagerSessionFftExt` still expose the one-axis forms;
  adding four n-dimensional methods to each was out of scope for this change.

## Verification conclusions and constraints

- `fftn` over three axes matches three sequential one-axis `fft` calls on
  random complex and real non-square grids; `axes` with one element is bit-identical
  to `fft`/`rfft`.
- A committed golden fixture (naive python DFT; NumPy is not installed on this
  machine, so the fixture is not `numpy.fft.fftn` output) pins `fftn` and
  `rfftn`, and the test also checks that `rfftn` is the non-negative half of
  `fftn` along the real axis. `rfftn`/`irfftn` round trips the grid.
- A transposed, non-contiguous `TensorView` (row-major strides over a compact
  buffer) gives the same result as the compact copy, a managed CPU tensor works
  through the same path as the one-axis call, and the eager entry point is
  verified to execute through the extension path.
- AD: `jvp` matches both the closed form (transform of the tangent) and central
  differences, and `vjp` matches the closed-form adjoint (`ifftn` with `Forward`
  normalization), in 1-D and 3-D. A separate adjoint-identity test covers
  requested lengths that pad one axis, truncate another, and pad a third, so the
  residual length restoration is exercised on every resized axis.
- Performance: 64^3 and 256^3 `C64` forward transforms show no measurable
  difference between `fftn` and a caller-written one-axis loop (the same loop).
  64^3: 8.66 ms versus 8.60 ms; 256^3: 1.390 s versus 1.386 s (one thread,
  `CpuEngine::serial()`, pinned to CPUs 0-3, criterion, 10 samples).
- CUDA was **not** executed: this machine has no GPU (`nvidia-smi` is absent).
  The CUDA path compiles and takes the same one-axis-per-step loop, i.e. one
  one-dimensional `cufftPlanMany` call per axis. A single multi-dimensional
  cuFFT plan is not implemented and is recorded as the remaining limitation in
  `docs/design/fft-backend-execution.md`.
