# CUDA owner-body move (issue #1929 B3(iii))

**Date**: 2026-09-26
**Branch**: `refactor/1929-session-route-unification`
**Scope**: the CUDA half of B3(iii) — move the CUDA operation bodies off the
backend owner so the session is the only operation route, matching what CPU and
WebGPU already do.

## Summary

`crates/tenferro-gpu/src/cubecl/ops.rs` now holds 57 free functions over
`&mut CudaBackend` — the bodies of `TensorElementwise`, `TensorAnalytic`,
`TensorStructural`, `TensorReduction`, `TensorDot`, `TensorIndexing`,
`TensorFusion` and the three `BackendSession` operations. The seven owner impls,
`impl BackendSession for CudaBackend`, `impl BackendCachedDot for CudaBackend` and
`CudaBackendSessionMarker` are deleted. `CudaExecSession` is the only operation
route, its impls generated by `delegate_ops!` (one list per family) forwarding
`ops::<op>(self.backend, ..)`.

## Context read

* `docs/design/explicit-session-boundary.md` — the B3(iii) reconnaissance, the
  per-operation work lists and the CUDA recipe written after four failed
  in-place attempts.
* `crates/tenferro-gpu/src/cubecl/mod.rs` (8744 lines), `exec_session.rs`,
  `blas1.rs`, `gemm.rs`, `dispatch.rs`, and the CPU (`exec_session.rs`) and
  WebGPU (`webgpu/exec_session.rs`) finals as the reference shape.

## Chosen design

The module-function shape, as the downloaded recipe prescribed: bodies move
verbatim, the receiver becomes an explicit `&mut CudaBackend`, and `self` is
renamed to `backend` by a string/comment-aware token rewrite. Two directions of
delegation are kept apart by macro: `delegate_ops!` for the moved families,
`delegate!` for the families that stay on the owner (`TensorBuffer`,
`TensorDeviceTransfer`).

Why not the WebGPU shape (bodies written straight into the session impls): the
CUDA bodies call many inherent `CudaBackend` helpers and pass `self` as an
argument to others, so an in-place move needs a dotted `self.backend.` rewrite in
macro-containing code. Four attempts at that produced between 215 and 1113
errors. The module-function shape needs only a plain rename and left six errors.

## Rejected alternatives

* **Keeping the owner impls and only re-pointing callers.** Fails B3: the owner
  would remain a second operation route.
* **`delegate!` with a per-method exception list.** The macro would need to
  special-case one method's receiver; an optional `override { .. }` group keeps
  the generated impl in one place and states the exception where it applies.
* **Leaving `elementwise_read_into` in `ops.rs` and calling the allocating
  fallback with the backend.** The fallback is generic over `TensorElementwise`,
  which the backend no longer implements.

## Residual risks

* The hardware-gated CUDA tests cannot run here. Verification on this host is
  compilation (`--features cuda --all-targets`), the retargeted source-text
  contracts and the non-ignored test targets; kernel behaviour stays with the
  hosted GPU matrix.
* `ops.rs` is 3300 lines. It is a mechanical container, not a new abstraction
  layer; if it needs splitting, split by operation family.
* The `delegate_ops!` `override` group accepts arbitrary items. It exists for one
  method yesterday and should stay that way; a second override is a signal to
  reconsider the shape.
