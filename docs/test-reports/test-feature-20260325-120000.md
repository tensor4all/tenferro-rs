## Per-Feature Details

### Tensor creation & manipulation
- **Role:** Condensed matter physicist with Python/NumPy background, new to Rust
- **Use Case:** Create tensors, perform view operations, verify column-major layout
- **What they tried:** from_slice, zeros, ones, eye, permute, broadcast, reshape, narrow, select, diagonal, contiguous
- **Discoverability:** Good. README quickstart + crate-level docs sufficient for basic usage. Missing: no element-level indexing method (`t.get(&[i,j])`), all doc examples use `ignore` attribute so they're not CI-verified.
- **Setup:** Worked perfectly. Only needed `tenferro-tensor` + `tenferro-device` (2 crates, not the 5 in README quickstart).
- **Functionality:** All operations produced correct results. Permute, broadcast, reshape, narrow, select, diagonal all worked as documented.
- **Expected vs Actual Outcome:** Matched. Two minor surprises: `is_contiguous()` is order-agnostic (returns true for either col or row-major); `reshape` always produces col-major strides regardless of input order.
- **Blocked steps:** None
- **Friction points:**
  1. No element-level indexing — must manually compute `buffer().as_slice()[offset + i*stride[0] + j*stride[1]]`
  2. `LogicalMemorySpace::MainMemory` verbose for CPU-only use
  3. `MemoryOrder` required for every constructor despite col-major being canonical
  4. No `Display` for element values — Debug only shows metadata
  5. Infallible operations like `zeros` on CPU return `Result`
- **Doc suggestions:** Add "minimal dependencies per use case" section; document `is_contiguous()` semantics; add NumPy equivalents table; make doc examples compilable

### Einsum
- **Role:** Physicist familiar with numpy.einsum
- **Use Case:** Matrix multiply, trace, outer product, dot product, matrix-vector, diagonal extraction/embedding
- **What they tried:** 7 einsum operations with numeric verification
- **Discoverability:** Good. README quickstart + crate docs include examples for all common operations. String notation is 100% NumPy-compatible.
- **Setup:** Worked on first attempt. 5 path dependencies, 155 packages, ~31s build.
- **Functionality:** All 7 operations passed with correct numeric results (matmul, trace, outer product, dot product, mat-vec, diagonal extraction, diagonal embedding).
- **Expected vs Actual Outcome:** Perfect match. NumPy-compatible notation works identically.
- **Blocked steps:** None
- **Friction points:**
  1. Column-major `from_slice` confusing for NumPy users — `[1,2,3,4]` with shape `[2,2]` gives `[[1,3],[2,4]]` not `[[1,2],[3,4]]`
  2. No direct data access — must chain `.contiguous(order).buffer().as_slice().unwrap()`
  3. Verbose type annotations: `einsum::<Standard<f64>, CpuBackend>(...)` for every call
  4. Mutable context threading (`&mut ctx`) unusual vs NumPy/PyTorch global state
  5. Some doc examples call `Tensor::zeros(...)` without `.unwrap()` — won't compile if copied
- **Doc suggestions:** Add "Column-Major for NumPy Users" callout; document data extraction pattern; fix `zeros` calls in batch examples; add NumPy equivalence table

### Linear Algebra
- **Role:** Physicist using numpy.linalg for SVD, eigendecomposition, solves
- **Use Case:** SVD, QR, eigen, eig, solve with mathematical verification via reconstruction
- **What they tried:** SVD (square + non-square), QR (with orthogonality check), eigen (symmetric), eig (general), solve
- **Discoverability:** Partial. README mentions linalg but has no quickstart example. Crate-level docs are excellent with working SVD examples. Individual function docs have examples.
- **Setup:** Worked. Default `linalg-faer` feature sufficient, no external BLAS needed.
- **Functionality:** All 6 operations passed. Reconstruction errors at or below machine epsilon (≤1.07e-14).
- **Expected vs Actual Outcome:** Matched well. API maps cleanly to numpy.linalg equivalents. Key differences: col-major layout, context parameter, thin SVD by default, 2D RHS required for solve.
- **Blocked steps:** None
- **Friction points:**
  1. No linalg quickstart in README
  2. `eigen` vs `eig` naming unclear — `eigen` is symmetric-only but name doesn't indicate this (numpy uses `eigh`)
  3. `solve` requires 2D `b` — no 1D vector support
  4. `num-complex` not re-exported but needed for `eig` return type
  5. Data extraction cumbersome (`.contiguous().buffer().as_slice()` chain)
- **Doc suggestions:** Add linalg quickstart to README; rename/alias `eigen` to `eigh`; document `solve` shape requirements; re-export `num_complex`; add `to_vec()` method

### Automatic Differentiation
- **Role:** Physicist familiar with PyTorch autograd and JAX autodiff
- **Use Case:** Compute gradients via reverse-mode (VJP) and forward-mode (JVP)
- **What they tried:** Reverse-mode `sum(exp(x))`, einsum matmul gradients, forward-mode JVP, dot product gradient, backward+leaf grad API
- **Discoverability:** Partial. README says "start from `tenferro`" but provides no AD example. Design doc shows low-level `tidu::Tape` API. Had to read integration tests and source doc comments to find the high-level workflow.
- **Setup:** Worked. Needed `tenferro`, `tenferro-tensor`, `tenferro-prims`.
- **Functionality:** All 5 tests passed. Reverse and forward mode both work. Gradients verified against analytical results and finite differences (< 1e-5 error).
- **Expected vs Actual Outcome:** Matched PyTorch autograd expectations — `set_requires_grad`, `backward`, `grad`, `zero_grad` all work as expected.
- **Blocked steps:** None
- **Friction points:**
  1. Must call `set_default_runtime(RuntimeContext::Cpu(...))` before any operation — not documented in README
  2. Two `Tensor` types: `tenferro::Tensor` (AD wrapper) vs `tenferro_tensor::Tensor<T>` (dense storage) share same name
  3. Value extraction verbose: `tensor.as_f64().unwrap().primal().buffer().as_slice().unwrap()`
  4. Trait method conflicts — `tenferro` imports bring `exp()` etc. that conflict with `f64::exp()`
  5. No `sub` or `mul` on `tenferro::Tensor` — requires negation+add or einsum
- **Doc suggestions:** Add AD quickstart to README; add AD examples to `tenferro` lib.rs; explain two-Tensor situation; document runtime setup requirement; add `to_f64_vec()` convenience method

### Custom Algebras
- **Role:** Physicist curious about tropical algebras for optimization
- **Use Case:** Use einsum with non-standard algebra (tropical/max-plus)
- **What they tried:** MaxPlus, MinPlus, MaxMul einsum operations via `tenferro-tropical`
- **Discoverability:** Partial. README mentions tropical conceptually but never says "use `tenferro-tropical`" or points to `extension/` directory. Design doc has incomplete pseudocode for user-defined algebras.
- **Setup:** Worked on first try. Required 6 crate dependencies.
- **Functionality:** All operations worked. MaxPlus matmul, trace, batch operations, MinPlus, MaxMul all correct.
- **Expected vs Actual Outcome:** Exceeded expectations — three tropical semirings ship out of box and work with einsum.
- **Blocked steps:** None
- **Friction points:**
  1. `tenferro-tropical` lives under `extension/` — non-obvious location
  2. Six-crate dependency list needed
  3. Defining a new algebra is non-trivial — design doc omits `TensorSemiringFastPath` requirement
  4. Plan-based doc example uses `ignore` attribute
- **Doc suggestions:** Add tropical quickstart to README; add "Custom Algebras" section; complete user-defined algebra pseudocode; consider facade crate re-exporting common crates

### C FFI
- **Role:** Physicist with C interop experience (ctypes/cffi), wants to call from Python/Julia
- **Use Case:** Exercise C API — tensor lifecycle, einsum, SVD, error handling
- **What they tried:** Built cdylib, generated header via cbindgen, wrote and compiled C program testing all major API functions
- **Discoverability:** Partial. README mentions C FFI but no C-specific quickstart. Crate-level docs excellent — design principles, inline C example, cbindgen command.
- **Setup:** Worked. `cargo build -p tenferro-capi` succeeded. cbindgen produced clean 626-line header.
- **Functionality:** Everything worked — tensor creation, shape queries, einsum (matmul + trace), SVD, error handling, cleanup. All results correct.
- **Expected vs Actual Outcome:** Exceeded expectations. Clean ABI with `size_t`, gcc compilation worked on first try.
- **Blocked steps:** DLPack interop (requires complex struct setup), AD rules (need reference gradient values)
- **Friction points:**
  1. Column-major not prominently documented in C API — `tfe_tensor_f64_from_data` says "implementation-defined"
  2. Linker dependencies (`-lm -lpthread -ldl`) undocumented
  3. No pre-generated header in repo
  4. Error message two-phase API verbose
  5. SVD AD rule cotangent shapes undocumented
- **Doc suggestions:** Add C API quickstart section; state column-major explicitly in `from_data` docs; ship pre-generated header; document linker flags

## Expected vs Actual Outcome

All 6 features achieved the expected outcome. The physicist persona was able to:
- Create and manipulate tensors (all view ops work)
- Run einsum with NumPy-compatible notation (100% compatible)
- Perform SVD, QR, eigen, solve with machine-epsilon accuracy
- Compute gradients via reverse and forward mode
- Use tropical algebras with einsum
- Build and use the C FFI from a C program

The main gap is **discoverability** — features work well once found, but the README funnels users only through the basic einsum quickstart. AD, linalg, tropical, and C FFI each require the user to discover the right crate and API pattern independently.

## Issues Found

### High Priority
1. **No AD quickstart in README** — The README's only advice is "start from `tenferro`" with no code example. Runtime setup (`set_default_runtime`) is undocumented.
2. **Column-major `from_slice` is a constant trap for NumPy users** — Every feature test hit this. Needs prominent warnings and concrete layout examples at every entry point.
3. **No element-level tensor indexing** — No `t.get(&[i,j])` or similar. Every test agent had to manually compute buffer offsets.
4. **No convenient data extraction** — Extracting values requires `.contiguous(order).buffer().as_slice().unwrap()`. Needs `to_vec()` or similar.

### Medium Priority
5. **Two `Tensor` types with same name** — `tenferro::Tensor` vs `tenferro_tensor::Tensor<T>` confusing for new users.
6. **`eigen` should be `eigh`** — Name doesn't indicate symmetric-only restriction.
7. **`tenferro-tropical` hard to discover** — Lives under `extension/`, not mentioned in README quickstart.
8. **Doc examples use `ignore`** — Not CI-verified, some have compile errors (missing `.unwrap()`).
9. **`num-complex` not re-exported** — Users of `eig` must add it as separate dependency.
10. **C API doesn't document column-major or linker flags**

### Low Priority
11. **Verbose constructors** — `LogicalMemorySpace::MainMemory` and `MemoryOrder::ColumnMajor` on every call.
12. **No `Display` for tensors** — Can't `println!("{}", t)` to see values.
13. **`solve` requires 2D RHS** — Unlike numpy which accepts 1D vectors.

## Suggestions

### Highest Impact
1. **Add "Getting Started" sections to README** for each major feature (tensor, einsum, linalg, AD, tropical, C FFI) with minimal working examples and required dependencies.
2. **Add `Tensor::get(&[usize]) -> Option<&T>`** for element access and `Tensor::to_vec() -> Vec<T>` for data extraction.
3. **Add prominent column-major layout warnings** with concrete examples at `from_slice`, einsum docs, and C API docs showing how `[1,2,3,4]` maps to a 2x2 matrix.
4. **Document `set_default_runtime` requirement** prominently in the `tenferro` crate docs and README.

### Medium Impact
5. **Rename `eigen` to `eigh`** or add alias to match numpy/PyTorch convention.
6. **Re-export `num_complex`** from `tenferro-linalg` or `tenferro-tensor`.
7. **Add a NumPy/PyTorch equivalence table** in main docs for common operations.
8. **Ship pre-generated `tenferro.h`** in repo or CI.
9. **Make doc examples compilable** — remove `ignore` where possible, fix broken examples.

### Lower Impact
10. **Consider convenience constructors** with col-major + CPU defaults to reduce boilerplate.
11. **Add `Tensor` Display impl** showing element values in matrix form.
12. **Consider facade crate** re-exporting common sub-crates to reduce dependency list.
