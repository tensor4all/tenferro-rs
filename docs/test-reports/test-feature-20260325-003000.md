## Per-Feature Details

### Quickstart & Tensor Basics
- **Role:** Mid-level Rust developer, new to tenferro
- **Use Case:** Follow README quickstart, test tensor creation/manipulation
- **What they tried:** README example, reshape, permute, broadcast, Debug display
- **Discoverability:** README quickstart compiles and runs. But `broadcast_to` in the design doc is actually `broadcast` in the API (minor naming inconsistency). No documented way to read tensor values back.
- **Setup:** Worked as described after adjusting dependency paths to absolute.
- **Functionality:** All operations pass: from_slice, reshape, permute, broadcast, einsum matmul with numerical verification.
- **Expected vs Actual Outcome:** Quickstart works. Numerical results correct (matmul verified element-wise).
- **Blocked steps:** None
- **Friction points:**
  - No `to_vec()`, no element indexing, no `Display` impl. Must use `buffer().as_slice().unwrap()` with manual offset/stride math.
  - `Debug` prints metadata only (dims, strides), not data values.
  - `LogicalMemorySpace::MainMemory` is verbose for CPU-only usage.
  - Column-major default surprises users from ndarray (row-major).
- **Doc suggestions:** Add "Reading Tensor Data" section; add element access method; extend quickstart to show reading results.

### Einsum
- **Role:** Scientific computing researcher, familiar with NumPy einsum
- **Use Case:** Matrix multiply, trace, outer product, dot product, batched, ellipsis, N-ary
- **What they tried:** 8 einsum operations including ellipsis and 3-input contraction
- **Discoverability:** Good. Crate docs show all common patterns.
- **Setup:** Worked.
- **Functionality:** All pass including ellipsis notation `...ij,...jk->...ik`.
- **Expected vs Actual Outcome:** All numerical results verified (matmul=[[23,31],[34,46]], trace=5, dot=14, etc.)
- **Blocked steps:** None
- **Friction points:** Type annotations `einsum::<Standard<f64>, CpuBackend>` are verbose for common case.
- **Doc suggestions:** Consider a convenience wrapper for the common `Standard<f64>, CpuBackend` case.

### Linear Algebra
- **Role:** Applied math grad student, familiar with scipy.linalg
- **Use Case:** SVD, QR, solve, det, inv
- **What they tried:** SVD+reconstruction, QR+reconstruction, solve Ax=b, det, inv
- **Discoverability:** Partial. SVD example in docs is good. But `solve` and `qr` take 3 args (no options), not 4 -- the docs show an `Option` parameter that doesn't exist.
- **Setup:** Worked after fixing API signatures.
- **Functionality:** All pass with numerical verification (SVD/QR reconstruction err < 1e-10, solve err < 1e-10, det=5 exact, inv*A=I exact).
- **Expected vs Actual Outcome:** Met. All linalg operations correct.
- **Blocked steps:** None
- **Friction points:**
  - `solve(&ctx, &a, &b)` takes 3 args, not 4. API signatures need checking against docs.
  - `qr(&ctx, &a)` takes 2 args, not 3.
  - Need `tenferro-einsum` dependency just to verify linalg results (for matrix reconstruction).
- **Doc suggestions:** Fix function signature documentation. Add result verification examples.

### Autodiff (Real)
- **Role:** ML engineer familiar with PyTorch autograd
- **Use Case:** VJP for sum, add, einsum, element-wise multiply
- **What they tried:** grad(sum(x)), grad(sum(x+y)), grad(einsum(a,b)), grad(sum(x*x))
- **Discoverability:** Partial. `grad()` and `set_requires_grad()` are documented. But reading gradient values requires navigating `as_f64().primal().buffer().as_slice()`.
- **Setup:** Worked with just `tenferro` + `tenferro-prims`.
- **Functionality:** All pass. Gradients computed correctly.
- **Expected vs Actual Outcome:** Met.
- **Blocked steps:** None
- **Friction points:**
  - No `to_vec()` on `tenferro::Tensor` -- reading values requires 4-5 chained calls.
  - `backward()` requires explicit `inputs` list (unlike PyTorch's `loss.backward()`).
  - `MemoryOrder` requires adding `tenferro-tensor` as dependency (not re-exported from facade).
- **Doc suggestions:** Add `to_vec_f64()`/`to_vec_c64()` convenience methods. Re-export `MemoryOrder`. Add complete AD tutorial example.

### Complex Tensor AD + Numerical Differentiation
- **Role:** Computational physicist, complex tensor expert
- **Use Case:** Complex64 einsum/linalg AD verified against finite differences
- **What they tried:** Complex einsum VJP, solve VJP, SVD VJP, 3-input einsum VJP, Cholesky VJP (real), all with numerical differentiation
- **Discoverability:** Partial. No public complex AD examples. Wirtinger convention (non-conjugated `sum(grad * d)`) is undocumented.
- **Setup:** Worked.
- **Functionality:** All numerical checks pass with correct convention:

| Test | Operation | Type | AD vs FD Error | Status |
|------|-----------|------|----------------|--------|
| BUG1 | einsum "ij,jk->ik" | Complex64 VJP | 1.08e-8 | PASS |
| BUG2 | solve | Complex64 VJP | 9.32e-11 | PASS |
| BUG3 | SVD (sum of singular values) | Complex64 VJP | 2.69e-10 | PASS |
| BUG5 | einsum 20x20 | Real VJP | rel_err 1.74e-6 | PASS |
| BUG7 | SVD non-square 3x2 | Real VJP | 9.54e-9 | PASS |
| BUG8 | 3-input einsum "ij,jk,kl->il" | Complex64 VJP | 2.65e-9 | PASS |
| BUG9 | Cholesky | Real VJP | 2.00e-10 | PASS |

- **Expected vs Actual Outcome:** All AD gradients match numerical differentiation within expected tolerance.
- **Blocked steps:** None
- **Friction points:**
  - Complex VJP uses non-conjugated convention (`sum(grad * d)` not `sum(conj(grad) * d)`). This is not documented and causes confusion -- initial tests failed with err=0.3 until the convention was understood.
  - Complex QR, LU, Cholesky, inv, det AD are primal-only (no gradient). The error message is clear but not in docs.
- **Doc suggestions:** Document Wirtinger convention explicitly. Add complex AD coverage matrix to docs.

## Issues Found

### Critical (bugs)

1. **[Critical] Complex chain AD (einsum + scalar op) produces wrong gradients**
   - Reproduction: `sum(exp(einsum("ij,jk->ik", a, b)))` on Complex64 tensors
   - VJP gradient does not match finite differences: error ~3e-4 (should be ~1e-8)
   - Neither non-conjugated (`sum(grad*d)`) nor Wirtinger (`Re(sum(conj(grad)*d))`) convention matches FD
   - Root cause: likely convention mismatch between einsum rrule (non-conjugated) and scalar exp rrule (Wirtinger conjugated) when chained
   - Note: einsum-only and exp-only complex VJPs pass individually

2. **[Critical] Trace einsum VJP ("ii->") fails with planning error**
   - Reproduction: `Tensor::einsum("ii->", &[&a])` then `grad(&[&tr], &[&a], ...)`
   - Error: `"output label 105 is not present in inputs"`
   - Affects both real and complex tensors
   - Diagonal extraction `"ii->i"` works fine; only scalar trace `"ii->"` fails

### Non-critical

3. **[Low] `broadcast_to` vs `broadcast` naming** -- Design docs mention `broadcast_to` but actual method is `broadcast`.
4. **[Low] `solve`/`qr` function signatures** -- Some linalg docs suggest an `Option` parameter that doesn't exist in the actual API.
5. **[Medium] No `to_vec()` or element access on `Tensor`** -- The most common user need (reading values) requires undocumented multi-step unwrapping.
6. **[Medium] Complex Wirtinger convention undocumented** -- Users will get wrong numerical results when verifying complex gradients without knowing the convention.
7. **[Low] `Debug` for `Tensor` shows metadata only** -- Surprising for users who expect to see data values.

## Suggestions

1. **Add `to_vec<T>()` or `to_vec_f64()`/`to_vec_c64()` to `tenferro::Tensor`** -- highest impact, most common need
2. **Document the complex AD Wirtinger convention** -- `sum(grad * d)` not `sum(conj(grad) * d)` for directional checks
3. **Add a complex AD example** to crate-level docs showing complete flow with Complex64
4. **Re-export `MemoryOrder` from `tenferro` facade** -- avoid needing `tenferro-tensor` as direct dependency
5. **Add complex AD coverage matrix** to supported-ops.md showing which linalg ops support complex AD
6. **Add element access method** `tensor.get(&[i, j]) -> Option<T>` for quick inspection
