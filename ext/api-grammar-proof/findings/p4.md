**Type home.** `MaterializationPolicy` had to live in tenferro-tensor (linalg and einsum cannot depend on the proof
crate). `ext/api-grammar-proof/src/policy.rs` should become `pub use tenferro_tensor::MaterializationPolicy;`
(not done: not my file). `p4_plan_policy::lower` is the temporary mapping.

**Name collision.** `ConcreteEinsumPlan` already has an inherent `execute_into(inputs, session, out)`. An inherent
method shadows a same-named trait method, so the adapter is `execute_into_with`. The real grammar change replaces the
inherent method, so this is a prototype-only wart.

## Findings

### SVD (`svd_read`)
- Compact: OK under both policies, same allocation count.
- Rank-2 transposed view: OK under both; read in place on native (allocations equal the compact-gathered baseline).
- Rank-2 negative-stride view: Allow succeeds and gathers (more operand-sized allocations than the compact baseline,
  and retained pool capacity > 0). Forbid returns `InputMaterializationForbidden { op: "svd", input: 0 }` with zero
  operand-sized allocations and the pool untouched (0 buffers, 0 bytes). The display text mentions `Allow`.
- Rank-3 batch with a strided batch axis: Allow gathers, Forbid refuses (same evidence).
- Dispatch is the same under both values: the predicate only decides refuse versus run the identical route.

### Reroute opportunity (finding, not implemented)
`svd_read` gathers every rank>2 non-compact view, but `tenferro_linalg::svd_with_exec` reads a rank-3 view with
non-negative strides in place: the test shows fewer operand-sized allocations than the gather route, and the same
singular values. So the Forbid refusal for the rank-3 case is imposed by the dispatch choice, not by the math. A
copy-free reroute is possible there, but would make dispatch policy-dependent (or, better, make Allow take it too).
Negative strides have no copy-free route: `svd_with_exec` rejects them (asserted in the test).

### Einsum
- Native CPU, N-ary (3 operands): transposed and negative-stride inputs allocate no more operand-sized buffers than
  the compact baseline (at edge 256, where tcontract's bounded packing buffers stay below one operand). Forbid
  therefore admits every layout and the new error is unreachable on native; the 3-operand compact route even
  allocates one more operand-sized buffer than the strided ones in this build (different strategy, not a copy of an input).
  Binary dot path: same result. `tcontract`'s own report documents `materialized: [false; 3]` and says bounded
  packing in the packed driver is not materialization.
- Caution about the proxy: at edge 32 transposed inputs showed one extra 16 KiB allocation (two 8 KiB operands'
  worth). That is a bounded pack buffer retained in the engine workspace (zero allocations on the second call), not an
  input copy; at edge 256 it vanishes. A test at small sizes would have misreported it as materialization.
- Eager fallback (`eager_einsum_exec*`: one operand, non-float dtypes, binary shapes that miss the dot shortcut,
  repeated labels): `TensorValue::into_tensor` / `tensor_owned` call `to_contiguous_read`, which copies even an owned
  compact tensor (`exec_session.rs:328`, "the copy below is this method's contract"). Test: `ij->ji` allocates at
  least one operand-sized buffer for compact, transposed and negative-stride inputs. By the ruling's definition (would
  not happen had the operand arrived in the consumed layout) these copies are NOT input materialization, because they
  happen for every layout. Consequence worth a ruling: Forbid is blind to them. A user who forbids copies still gets
  a copy of every operand on this path. I treated them as admitted; the alternative (count any `to_contiguous_read`)
  would refuse every eager call including compact input.
- Plan reuse: `prepare` records dtype and shape only (`cpu_cache_stats().entries == 0` after prepare). Execution on
  compact layouts misses once and installs one entry; the same layouts hit; each change to transposed, negative or
  mixed strides misses exactly once and evicts (single-entry cache); repeating a strided layout hits. Results equal a
  gathered-compact reference in every case, under Forbid.
- Cache key and policy: the policy is not in the cache key, and with this hook it need not be. The check runs before
  the cache lock, and on native dispatch does not depend on the policy, so a plan cached under Allow runs the same
  non-copying kernel under Forbid. That safety is conditional: on a build where an operand can be packed depending on
  layout (blas), the same cached plan would copy under Forbid unless the hook gains a per-layout predicate, or the
  key includes the policy.
- Validate-before-side-effects: with a bad operand 2 (shape) and awkward operand 0, `execute_into_with` fails under
  both policies with a non-policy error, `out` is byte-identical to its prefill, and no plan was built
  (`misses == 0`). The policy refusal itself could not be exercised on einsum (unreachable on native), so
  "out untouched on a policy refusal" is shown only through the validation path, which runs first.

## Not verified
- BLAS build (`cpueinsum-blas`): compiled only. `BlasStep::packed()` (cpueinsum-blas `layout.rs` ~276-319) packs whole
  operands whose layout a step cannot consume; that is input materialization. The hook goes in
  `tenferro-einsum/src/cpu_concrete.rs` `operand_materializes` (blas variant, now `None` so Forbid returns
  `Unsupported`): after the plan is built (`prepare` closure in `run_into`, before `with_scratch`), ask the plan which
  steps pack which input and map that to the operand index. Because it needs a plan, the check would then sit after the
  cache lookup, so a cached Allow plan would be inspected rather than rebuilt; keep it before any write to `out`.
  The blas SVD predicate (`is_owned_layout`) compiles but was not run.
- GPU/CUDA sessions: Forbid is refused as `Unsupported` by design; not exercised.
- Integer/bool einsum and non-CPU einsum eager paths were not measured beyond the f64/c64 `ij->ji` case.
- The allocator proxy counts allocations on the calling thread only; a threaded engine could copy elsewhere. All
  measurements use `CpuEngine::serial()`.
