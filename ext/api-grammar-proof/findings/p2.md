# P2: einsum destination (`Dest`) and spec (`EinsumSpec`)

Files: `src/p2_einsum_dest.rs`, `tests/p2_einsum_dest.rs`. Adapter over the unchanged
`ConcreteEinsumPlan` (crates/tenferro-einsum/src/concrete.rs). "complex64" here means
`DType::C64` = `Complex<f64>` (the repo's naming).

## What was built

- `EinsumSpec<'a>`: `Text(&str)` / `Subscripts(&EinsumSubscripts)` / `Notation(&EinsumNotation)` /
  `Indices(EinsumSubscripts)` (owned, from `EinsumSpec::indices(&[&[u32]], &[u32])`). `From<&str>` only wraps;
  parsing and validation happen inside the op and come back as `Err`.
- `EinsumOptions` (builder: `with_optimize`, `with_conj(Vec<bool>)`), `Dest<'a>` =
  `Overwrite | Accumulate | Scaled { out, alpha, beta }` over `TensorWrite<'a>` (scalars are `ContractionScalar`).
- Extension trait `EinsumInputs` on `[TensorRead<'_>]` with `einsum(spec, exec)`,
  `einsum_with(spec, &opts, exec, policy)`, `einsum_into(spec, &opts, exec, policy, dest)`.
  Mapping: `prepare_read*` then `execute_read` / `execute_read_into` (Overwrite, no conj) /
  `execute_read_into_accum` (everything else). Errors are `tenferro_tensor::Error`
  (`EinsumError::into_tensor_error`). `Forbid` returns `tenferro_tensor::Error::Unsupported` before any side effect.

## Commands and results

```
RUSTFLAGS="-Zcrate-attr=feature(atomic_try_update)" cargo +nightly test --ignore-rust-version \
  -p tenferro-api-grammar-proof --test p2_einsum_dest
```
Last run: `13 passed; 0 failed` (debug profile, CpuEngine::serial()).

Covered: binary `ij,jk->ik` and ternary `ij,jk,kl->il` (complex, non-symmetric data, expected values from an
independent naive loop in the test); all four spec forms give identical results; Overwrite over garbage;
Accumulate; Scaled with complex alpha and beta; beta == 0 with NaN-prefilled output for binary and ternary
(`0+0i`, `-0+0i`, `0-0i`) and Overwrite over NaN: no NaN leaks. Control: beta != 0 over NaN does propagate NaN.
Bad specs (no arrow, output label absent from inputs, term count != input count, rank mismatch, empty text,
dimension mismatch for a shared label, empty input slice, trailing `->`) are errors, never panics.

## Findings

1. **Conjugation is silently dropped whenever there is no `BinaryDotPlan`; it is honoured only on the binary dot path.**
   `execute_read_into_accum` (concrete.rs:1854, reset at 1880, line numbers at HEAD fb8dc92d; another prototype has since edited that file) and `eager_einsum_exec_read_into_accum`
   (eager.rs:1235) overwrite `lhs_conj`/`rhs_conj` with `false` before `accumulate_dot_result_into`.
   Observed (pinned in tests, request returns `Ok`):
   - `ij,jk->ik` conj on lhs/rhs/both: honoured (also with Accumulate).
   - `ij,jk->ki` (binary, transposed output): honoured.
   - `ii,ij->j` (binary, repeated label, no dot plan): **dropped**.
   - `ij,jk,kl->il` with conj on operand 0 (CPU N-ary branch, `crate::cpu_concrete::supports`, which requires >= 3
     inputs): **dropped**. Same through the raw plan API with `lhs_conj = rhs_conj = true`, so the adapter is not the cause.
   - The non-CPU fallback for N >= 3 (eager.rs:1235) has the same reset; I could not exercise it (no non-CPU engine
     in this prototype), so that is read from source only.
   Not an error and not documented in the `execute_read_into_accum` doc, which advertises `DotGeneralAccumulation`.
2. **N-ary conjugation cannot be expressed at all.** `DotGeneralAccumulation` has exactly two flags (lhs/rhs), a
   pairwise-dot notion; a per-operand `conj` option has no carrier for operand 3+. The adapter returns
   `Unsupported` for conj on operand >= 2, but cannot reject conj on operands 0/1 of an N >= 3 einsum or on a binary
   einsum without a dot plan, because whether a dot plan exists is private to the plan (`binary_dot`). A correct
   implementation needs either conj materialization up front (an input copy, which interacts with
   `MaterializationPolicy::Forbid`) or per-step conj inside the contraction tree. The grammar's "conjugation is
   operation configuration" holds, but today's execution layer can only carry it for one shape of call.
3. **No conj on the value-returning path.** `execute_read` has no accumulation argument, so
   `einsum_with(.., conj)` is `Unsupported` in the adapter. A fresh-output conj call would have to allocate the
   destination first (the plan's output shape is private).
4. **`optimize` cannot be honoured by the concrete layer.** `ConcreteEinsumPlan::prepare*` takes no optimizer
   argument and always plans with `ContractionTree::optimize` (eager.rs:312). Only `EinsumOptimize::Auto` is
   accepted by the adapter; `False`/`Nested`/`Path`/`Tree` are `Unsupported`. The traced layer does take
   `EinsumOptimize`, so one option type spans two layers with different capability sets.
5. **No-read guarantee at beta == 0 holds** on both paths tested: Overwrite goes through `execute_read_into`; Scaled
   with beta == 0 relies on `accumulate_typed` (tenferro-tensor/src/backend.rs:606+, `beta_is_zero` branch,
   `-0`/`+0` complex zero included). But the N-ary accumulate path computes into a full temporary (`execute_read`)
   and then copies: it needs a temporary of output size, and the "overwrite" N-ary guarantee is implemented
   separately (CPU `execute_into`) from the Scaled(beta=0) guarantee.
6. **Error type is not uniform.** The concrete einsum API returns `tenferro_einsum::Error`, not
   `tenferro_tensor::Error` (the proposal's concrete-layer type). The adapter converts with `into_tensor_error`:
   parse failures become `Error::Extension { family: "tenferro.einsum.v1", kind: Validation(InvalidArgument),
   source: InvalidSubscripts }`, while arity/rank mismatches become plain `Validation` errors. The same mistake
   class thus lands in two variants.
7. **Spec surface**: there is no single public parse/validate entry for the three spec forms; the plan has
   `prepare_read`, `prepare_read_subscripts`, `prepare_read_notation`, so the unification is a four-arm match in the adapter,
   not a conversion. `EinsumNotation` accepts ellipsis; `EinsumSubscripts` does not.
8. Digit labels are valid (`"i1,jk->ik"` is accepted), and `"ij,kl->ik"` is a legal expression (unmatched labels are
   summed); neither is an error, which surprised me while writing bad-spec cases.

## Not verified

- Non-CPU engines (the eager fallback path for N >= 3 and any GPU provider); strided/non-compact destination views
  (`compact_host_accumulation_slice` falls back to per-element writes, untested here).
- f32/c32 and real dtypes; only C64 is covered.
- Release-profile behaviour; no performance measurement for P2.
- Aliasing between `dest` and an input.
