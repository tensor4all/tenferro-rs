# P7: the borrowed-`Exec` entries and lane splitting as ordinary grammar

Files: `crates/tenferro-cpu/src/borrowed_engine.rs` (hooks), `src/p7_borrowed_engine.rs` (adapter),
`tests/p7.rs` (15 tests), `tests/p7_allocation.rs` (2 tests, own binary with a counting allocator),
2 `compile_fail` doctests in the adapter module. Nothing committed.

Question: can the six `*_with_exec` functions of tenferro-linalg (#2462) be deleted, so that
`view.svd_with(&opts, &mut BorrowedCpuEngine::new(exec, &mut pool))` replaces
`svd_with_exec(exec, &mut pool, &view, full)`? Answer from this prototype: **yes for the four
conditions below, with two behavioural findings (F1, F2) and a real cost (the `Engine` surface).**

## Decision

**Chosen: (A) a carrier engine, plus a lane API on top of it.** `BorrowedCpuEngine<'a, 'e>` holds
`&'a mut Exec<'e>` and `&'a mut BufferPool` and is an `Engine`; `CpuEngine::with_lanes(shares, pools, f)`
forks the engine's token and gives each lane such an engine. The adapter finds the bundle and pool behind
`&mut dyn Engine` and calls the existing typed bodies.

| | Meets 1 lifetimes | 2 reuse/zero alloc | 3 nested + concurrent | 4 no retention | Cost | Verdict |
|---|---|---|---|---|---|---|
| **A** carrier `BorrowedCpuEngine` | yes (HRTB visitor, one `unsafe` cast, no extension) | yes, equal to `with_exec` | yes | yes | 48 required `Engine` methods answering `Unsupported`, ~350 generated lines | **smallest that works** |
| **B** `CpuEngine` made borrowable | would need `CpuEngine<'a>` (lifetime on the public type: every `struct S { e: CpuEngine }` changes) or an owned/borrowed enum that still needs a lifetime | would work | would work, and lanes could run einsum and core ops | would work | ~37 `resources`/`parts()` sites in `exec_session.rs` plus `engine.rs`, 12 `Engine` impls generic over the host, public type change | right end state, too big for P7; see "What the real implementation needs" |
| **C** no borrowed engine, one ordinary `CpuEngine::serial()` per lane | n/a | pool is the lane engine's own, not the caller's | **partial**: concurrent and correct, but ignores the share | n/a | none | **loses**: cannot meet #2462's "sub-teams of one engine" |
| **A0** wrapper that is not an `Engine`, calls the six functions | yes | yes | yes | yes | none | loses on purpose: every op would need a second receiver kind next to `&mut dyn Engine`, which is exactly what #2552 removes |

Why C loses, measured (`design_c_per_lane_serial_engines_run_concurrently_but_ignore_the_share`):
lane 0 was given a share of 3 slots and its serial lane engine used 1 thread (`num_threads() == 1`); lane 1
share 1, used 1. Results were bit-identical to the reference, so C is a correct fallback for callers that do not
care about the share, but the "sub-team" of #2462 is not honoured. A lane engine of its own would also have to be
built (ArenaProvider, plan cache) and kept across calls to stay allocation-free.

## The four conditions

**1. Lifetimes: VERIFIED.** The test `the_borrowed_engine_is_a_dyn_engine_over_borrowed_exec_and_pool_without_static`
builds `Exec::serial()` and `BufferPool::new()` as locals, coerces `&mut BorrowedCpuEngine` to `&mut dyn Engine`, runs
two grammar calls, ends the borrow with a block and uses the pool and bundle again. No `'static` bound exists anywhere.
The path from `&mut dyn Engine` back to the bundle is `Engine::native_engine()` with a crate-private marker (the
existing `with_cpu_engine` mechanism) and `with_borrowed_cpu_engine(engine, |exec, pool| ..)`. That visitor contains one
`unsafe` pointer cast, like `with_cpu_engine`. It is not a lifetime extension: the callback is higher-ranked over the
bundle's lifetime (`impl FnOnce(&mut Exec<'_>, &mut BufferPool)`), so it cannot name or lengthen what the engine was built
with. "No unsafe" is not what holds; "no unsafe lifetime extension" is. A reviewer should read that one cast.

**2. Buffer reuse / zero allocation: VERIFIED** (`tests/p7_allocation.rs`, steady state = fewest allocations of four
rounds, counting allocator, rank-8 operand included):

```
p7 alloc svd/48: with_exec 0, grammar on borrowed engine 0       (also svd_full/48, svdvals/48, qr/48,
p7 alloc eigh/48 / eigvalsh/48 / eigvals/48 / svd/complex64 / qr/rank8: all 0 and 0
p7 alloc qr/48 serial: with_lanes 1, with_exec + BorrowedCpuEngine 0     (reported, not asserted)
```
Identical in debug and `--release`. Constructing `BorrowedCpuEngine::new` and the `dyn` coercion inside the measured
window allocate nothing. Pool half (`every_buffer_comes_from_the_callers_pool_and_the_engines_pool_is_untouched`):
all seven operations on a `[4,3,2]` complex batch fill the caller's pool to 5 buffers / 4976 bytes; the engine's own pool
stays at 0 buffers before and after; a second round leaves the caller's pool unchanged. Not measured: rank 9 (the
metadata spill documented in #2505) was not repeated here; the grammar adds nothing to it by construction, but I did not
run it. `with_lanes` itself costs 1 allocation per call (the result `Vec`/slot vector), measured on a serial engine; the
threaded fork cost was not measured.

**3. Nested and concurrent execution: VERIFIED for linalg, with the limits below.**
- `nested_in_with_exec_and_with_contraction_exec`: serial and 2-thread engines under `with_exec`, and `with_contraction_exec`
  (which lends the engine's *own* pool: it fills that one). Results bit-identical to the `with_exec` entry; the outer
  engine is not broken and answers an ordinary `qr` afterwards.
- `concurrent_lanes_from_fork_sized_and_from_token`: a 4-thread team engine (`has_team()` asserted), inside
  `with_exec`, `exec.token().fork_sized(&[3, 1], ..)`, each lane builds `Exec::from_token(child, workspace, policy)`
  (docs/guides/cpu-execution.md "Lanes") and a `BorrowedCpuEngine` over a lane pool. Lane 0 ran a 24x24 QR on a share of
  3 and lane 1 a 20x20 Hermitian `eigh` on a share of 1 (the lane engine's `exec.budget()` is asserted 3 and 1). Results
  bit-identical to the single-lane reference; both lane pools used, the engine's pool at 0; engine not broken.
- `with_lanes_runs_ordinary_grammar_calls_concurrently`: the same through the new hook, `[2, 2]`: an SVD and an `eigvalsh`
  in parallel through `view.svd(engine)` with `engine: &mut dyn Engine`.
- No deadlock and no re-entry: every concurrent test runs on a helper thread with a 60 s watchdog; all finished in
  milliseconds. Re-entry of the outer engine is a type error (`with_exec` holds `&mut CpuEngine`), so the lanes cannot
  reach it; invalid splits (shares `[3, 2]` summing to 5 on a 4-slot engine, a zero share, a length mismatch) are typed
  validation errors and leave the engine usable.
- Panic in a lane: `fork_sized` re-raises after every lane finished and `with_exec` marks the outer engine broken
  (`a_panic_in_a_lane_breaks_the_engine_like_a_panic_in_with_exec`); a broken engine refuses `with_lanes`.
- Not verified: that the *provider* really ran multi-threaded inside a lane (no ledger or timing used; only the budget
  the lane engine reports is asserted); speedup; oversubscription behaviour with a share larger than the work.

**4. No retention past the call: VERIFIED.** The borrow checker part: two `compile_fail` doctests, `drop(pool)` while the
engine lives is E0505, and an engine outliving its `Exec` is E0597. The runtime part (`outputs_may_outlive_the_borrowed_engine_and_the_pool`),
which is the same for the existing `with_exec` entry because the mechanism is in the pool, not in the engine:
- A pool output's recycler is `Weak<dyn HostBufferRecycler>` (`pool_finish_recycled` downgrades the pool's `Arc`), the pool
  is an `Arc<SharedPool>`. Nothing in the engine path stores a pool buffer, an `Exec`, or the engine.
- Engine gone, pool alive: dropping the outputs returns Q and R to the pool (held buffers `n`, after drop `n + 2`).
- Engine and pool both gone: the output is plain owned storage; reading and dropping it is fine and it retains nothing
  (the weak handle is dead). Outputs also move to another thread after the lanes, pools and engine are dropped
  (`lane_outputs_are_sendable_after_the_lanes_end`).

## Parity with the `*_with_exec` entries

- Results: `grammar_results_are_bit_identical_to_the_with_exec_entries_{f64,complex64,single_precision}`: svd thin and
  full, svdvals, qr, eigh, eigvalsh, eigvals, on compact, strided, batched, zero-dimension and square-strided views,
  for f64, Complex64, f32 and Complex32; shape, placement and `Debug` text of every value equal. The same grammar call on
  an ordinary `CpuEngine` (via `with_contraction_exec`) is bit-identical too.
- Errors: `errors_have_the_same_kind_variant_and_source_as_the_with_exec_entries` (rank 1, non-square, NaN input: kind,
  `Debug` of the variant and the downcast `tenferro_linalg::Error` payload equal) and
  `a_negative_stride_is_unsupported_with_the_same_message_for_every_entry` (all seven entries, non-empty and empty
  operand: `ErrorKind::Unsupported`, equal variant and message).

## Findings

- **F1. One grammar, two input rules.** The borrowed typed route refuses a negative stride; the erased engine route
  (`svd_read`) gathers it. With `view.svd(exec)` on a typed view the engine kind must not change the rule, so the adapter
  keeps the *borrowed* rule on both `BorrowedCpuEngine` and `CpuEngine` (tested: `reversed.svd(&mut cpu)` is `Unsupported`
  while `svd_read` of the same data succeeds). Deleting the six functions therefore means choosing one rule for typed-view
  receivers in the real grammar; it cannot be both. (with_exec.rs already documents the three rules; the grammar would have
  to say which receiver gets which.)
- **F2. No gauge on the borrowed route.** `svd_with_exec` has no gauge/driver parameter, so `svd_with` on a borrowed
  engine refuses a non-`Raw` gauge with `Unsupported` (same limitation as P1's full-matrices case) and accepts `driver`
  without effect.
- **F3. The carrier is an engine that is almost not an engine.** `Engine` requires 48 methods (Structural 8, Elementwise 14,
  Analytic 11, Reduction 4, Indexing 8, Dot 1, DeviceTransfer 2) plus three empty impls and `native_engine`; roughly 40
  provided methods fall through to the required ones. All of them answer `Unsupported` ("needs a CpuEngine"), including the
  erased `Tensor::svd(&mut borrowed)` entries (tested). That is the design smell the brief predicted, measured: a public
  type whose operations are refused cannot be offered as an engine to users. It is only acceptable as a `#[doc(hidden)]`
  lane type that the caller meets as `&mut dyn Engine` inside `with_lanes`.
- **F4. A lane has no einsum/core.** Because of F3, a lane runs linalg only. The use case in #2462 (factorizations on
  sub-teams) is covered; a lane that wants a contraction before its SVD is not.

## `with_lanes` design questions

`CpuEngine::with_lanes(&mut self, shares: &[usize], pools: &mut [BufferPool], f: impl Fn(usize, &mut dyn Engine) -> R + Sync) -> Result<Vec<R>>`
(`#[doc(hidden)]`; `with_exec` then `exec.token().fork_sized_slots(..)`, one `Exec::from_token` bundle per lane).

- **Pools: caller-provided.** The pool must outlive a lane to stay warm across calls (steady-state zero allocation is a
  property of reusing the same pool), and #2462 callers already hold per-lane pools. Engine-owned lane pools would need a
  `Vec<BufferPool>` field on `CpuEngine`, a rule for resizing it when the split changes, and the retention limit applied per
  lane; that is convenient but additive and can come later. Caller pools keep condition 2 literally ("from the caller's pool").
- **Per-engine state inside a lane** (what the prototype does, and what a full lane would do):

| State | In the prototype lane | Full lane |
|---|---|---|
| Thread budget / token | per lane: the child share | same |
| Workspace arena (`WorkspaceProvider`, `Sync`) | shared, the parent's, forwarded to the child bundle | same; it is thread-aware by design |
| Batch policy | per lane, copied (`BatchPolicy` is `Copy`, travels in the bundle) | same |
| Buffer pool | per lane, caller-provided | same |
| Plan cache (`CpuPlanCache`, `Arc<Mutex<..>>`) | unavailable (no einsum in a lane) | shared by handle clone; lanes would contend on its mutex |
| Extension caches (`ExtensionCacheStore`, owned inline, not `Sync`) | unavailable | per-lane store, or unavailable; cannot be shared without a lock |
| Allocation domain (`Arc<dyn Send + Sync>`) | **not forwarded**: a lane's outputs are not bound to the engine's domain | shared read-only; needs forwarding |
| `broken` flag | outer only: a lane panic is re-raised after all lanes finish and breaks the outer engine; a lane cannot mark itself | same |

- **Does `with_lanes` remove the need for `BorrowedCpuEngine`?** Not in this prototype: it is built on it. If lanes
  became full engines (B) the carrier would disappear as a public type and only `with_lanes` would stay public. Until then,
  `BorrowedCpuEngine::new(exec, pool)` remains the only way for a caller who is *already* inside a token they did not get
  from `with_lanes` (their own fork, a foreign scheduler) to use the grammar. `with_lanes` is the better default API
  (shares are checked, the token is never cloned, the total stays under the budget, no raw Rayon), and it makes a hand-built
  bundle unnecessary for the common case.

## What the real implementation would need

1. Keep the six typed bodies as `#[doc(hidden)]` crate-visible entries (today they are `Sealed::*_with_exec` plus the
   public functions) and add a branch to `with_linalg_backend` (`tensor_ext.rs:2653`) that recognizes the borrowed marker,
   next to the CPU and CUDA branches. This prototype puts that dispatch in the adapter instead.
2. Decide F1 and F2 (one input rule for typed views; whether `SvdOptions` gets a borrowed-route variant).
3. Decide between A-as-lane-only (what is here) and B: make the `CpuEngine` internals generic over where `Exec` and
   `BufferPool` come from. About 37 `resources`/`parts()` sites in `exec_session.rs`, `engine.rs` and `contraction.rs`, the
   12 `Engine` impls, and a lifetime on whichever type carries a borrowed bundle. That is the change that also gives lanes
   einsum and core ops and removes F3/F4. It is a refactor of the CPU engine, not a prototype-sized edit.
4. Docs: `docs/guides/cpu-execution.md` "Lanes and the vendor provider" would describe `with_lanes` instead of hand-built
   bundles.
5. GPU: nothing here applies; a CUDA lane would need its own design (streams, not a token).

## Risks

- The `unsafe` cast in `with_borrowed_cpu_engine` is new and has the same shape as `with_cpu_engine`; its soundness rests
  on the HRTB callback and the private marker. It deserves an audit and a Miri run (not done here).
- A public engine that refuses 48 operations will surprise users; keep it hidden or finish B.
- `with_lanes` requires `Fn + Sync` closures and `R: Send`; `fork_sized_slots` already enforces it, but it makes
  non-`Send` lane results impossible.
- Per-lane `broken` handling is coarse (one lane's panic breaks the whole engine).

## Not verified

BLAS builds (not compiled), GPU engines (nothing claimed), rustc 1.96, Linux, rank-9 operands on the borrowed grammar,
real multi-thread speed-up inside a lane, Miri, `with_lanes` allocation count on a team engine.
