# P1: complex SVD across input forms

## Built
- `src/p1_svd.rs`: `Svd<V, R = V> { u, s, vh }` + `into_parts()`; `SvdShape { Thin, Full }`;
  `#[non_exhaustive] SvdOptions { shape, gauge, driver, derivative_eps }` with `Default` and builder
  setters; trait `SvdOps` (`svd(engine)`, `svd_with(&opts, engine, policy)`) implemented for `Tensor`,
  `TensorRead<'_>`, `TypedTensor<T>` and `TypedTensorView<'_, T>` (`T: LinalgScalar`).
- ONE internal function `svd_erased(TensorRead, &opts, engine, policy)`; all four receivers call it.
  Typed receivers erase (`T::tensor_read` / `into_tensor_read`, metadata only) and downcast the three
  outputs with `downcast_checked` (`T::into_typed`, returns `Error::Validation(DTypeMismatch)` on mismatch).
- `svd_typed_view_direct`: second, direct route (typed view -> `tenferro_linalg::svd_with_exec`) written
  only to measure the cost of the "one implementation" claim.
- `Forbid` -> `Error::unsupported("svd", "... enforcement is not implemented by any provider yet")`.

## Tests
`RUSTFLAGS="-Zcrate-attr=feature(atomic_try_update)" cargo +nightly test --ignore-rust-version -p tenferro-api-grammar-proof --test p1_svd`
-> **15 passed, 0 failed, 0 ignored**.
Covered: c64 thin 3x2, 2x3, batch 3x2x2; c64 full 3x2, 2x3, batch 2x3x2, each over owned erased, `TensorRead`,
typed owned, typed view, transposed view (typed and erased), direct route (reconstruction A ~ U diag(S) Vh
< 1e-12, `s` equal across forms, `s` dtype F64, output shapes); f64 thin/full; negative-stride view;
Full + gauge; eps validation; driver; Forbid on all forms; checked downcast; rank-1 input.

## What the grammar fits
- `Svd<V, R = V>` works: complex gives `Svd<TypedTensor<C64>, TypedTensor<f64>>` (compile-time asserted),
  real collapses to one type. The erased form has `R = V = Tensor`.
- The four receivers do funnel into one function, with no copy on entry (`T::tensor_read`,
  `into_tensor_read` are metadata-only). Typed in -> typed out holds at the type level.
- This is what `TypedTensorLinalgExt` already does today (tensor_ext.rs:2362-2390: `svd_read` then
  `typed_svd`), so the typed path was never "typed all the way down".

## What it could not express (pinned by tests)
1. **Typed borrowed cannot avoid erase + downcast and keep the options.** The only typed borrowed entry
   is `svd_with_exec(exec, &mut BufferPool, &TypedTensorView, full: bool)` (with_exec.rs:63). It has no
   gauge/driver/eps, takes `full: bool` (the proposal's banned flag), needs a `&mut Exec` that is reachable
   from `&mut dyn Engine` only via the `#[doc(hidden)]` `tenferro_cpu::with_cpu_engine` (cpu/src/lib.rs:224)
   + `CpuEngine::with_exec`, and is host-CPU only. So there are two real implementations; "one
   implementation" holds only if the typed view goes through the erased route.
2. **The downcast is checked** (`T::into_typed` -> `Result`), but the existing private `typed_output`
   (tensor_ext.rs:2711) turns a mismatch into `Error::Internal(String)`; mine returns a typed
   `Validation(DTypeMismatch)`. Cannot fail for an honest backend; it is a contract assertion.
3. **Negative strides: two rules survive behind one grammar.** Under `Allow`, the erased route gathers
   (`*_read` rule); the direct typed route returns `Unsupported`. The same `TypedTensorView` gives different
   outcomes depending on which internal route the typed impl picks (with_exec.rs:11-13 documents this and a
   test, `a_negative_stride_is_unsupported_for_every_entry`, deliberately pins it). A single grammar entry
   must choose one: choosing the erased route makes typed views accept negative strides; choosing the
   direct route makes `Allow` refuse a layout it claims to normalize.
4. **Full + non-Raw gauge is not expressible.** `svd_with_options(_read)` is thin only (backend.rs:231,
   :434 call `svd`/`svd_read` then `apply_svd_gauge`); `svd_full(_read)` takes no options (backend.rs:~250).
   `apply_svd_gauge` is `pub(crate)` (extension.rs:1290), so the adapter cannot compose them. The adapter
   returns `Unsupported` for `Full + CanonicalPivot`; this needs a linalg change (take shape and gauge in
   one backend entry), not a wrapper. A `SvdShape` enum cannot hide that.
5. **`derivative_eps` is only validated on the thin path** (`validate_derivative_eps` inside
   `svd_with_options*`); `svd_full*` has no eps parameter. The adapter validates once up front so both shapes agree.
6. **`driver` is accepted and ignored by `svd`** (the CPU backend never reads it; outputs are bit-identical
   for Auto/Jacobi/QrBased, tested). An option field that does nothing is an API smell the grammar inherits
   from `SvdOptions`.
7. **Two real-scalar names.** `LinalgScalar::RealScalar` (svd_with_exec output) and `TensorScalar::Real`
   (typed_svd output) are unrelated associated types to the compiler. The direct route needs the explicit
   bound `T: LinalgScalar<RealScalar = <T as TensorScalar>::Real>`; a generic `SvdOps` impl over the direct
   route would carry it in the public bound. Worth unifying before a public `Svd<V, R>` is frozen.
8. `Svd<Tensor>` for erased inputs loses the "complex => real s" fact at the type level (only the runtime
   dtype says F64); acceptable but real.

## Surprises
- `TypedTensorView::into_tensor_read` and `T::tensor_read(&TypedTensor)` made the erasure trivial; no new
  trait was needed (the proposal's `AsView` is not required for these four receivers).
- Everything compiled first try with `&mut dyn Engine`; `CpuEngine` is the only engine exercised.

## Not verified
GPU/CUDA engine; non-host placement; `Forbid` semantics (not implemented anywhere); eager/traced SVD;
autodiff through the adapters; performance/copy counts (I did not instrument allocations, so "no copy on
entry" rests on reading the code, not a measurement); f32/c32; zero-sized dims; `SvdGauge::CanonicalPivot`
numerical properties beyond thin shape.
