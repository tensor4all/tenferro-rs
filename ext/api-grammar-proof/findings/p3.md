## Built
- `src/p3_fft_consume.rs`: `FftOptions { axis: isize, norm: FftNorm }`, `IfftOptions` (same fields),
  trait `SessionFftConsumeExt` on `EagerSession` with `fft_in_place` / `ifft_in_place`

## Key question: can a session extension reach the engine?
Yes. `EagerSession::engine(&mut self) -> &mut dyn ExecutionEngine` is public (crates/tenferro-ad/src/eager.rs:2515),
documented for exactly this. No internal hook is needed. Calling the engine-taking consuming API from inside
`with_eager_session` does not trip reentry and does not add a reference to the input (the shared-owner test
distinguishes a real clone from the session; a sole owner created by `session.constant_from` is accepted).
So the session-receiver form is a thin shim today; the engine-argument methods on `EagerTensor` can be demoted or removed.

## What the grammar could not express / did not fit
1. No length option: the in-place API fixes `n = None` (eager_in_place.rs, `concrete_fft_spec(..., None, ...)`). `FftOptions`
   therefore has no `n`, unlike out-of-place `fft(input, n: Option<usize>, axis, norm)` (eager_ext.rs). Two option shapes will diverge
   unless out-of-place also moves to `FftOptions` with an `n` that in-place rejects.
2. `FftOptions` and `IfftOptions` are identical; the split is only for symmetry with decided naming. One type would do.
3. `Forbid` is vacuous for this op: in-place already rejects non-compact input (eager_in_place.rs, `is_col_major_contiguous` check)
   and never materializes. A truthful implementation would accept `Forbid` today. Per the task it returns "not implemented" instead,
   which makes a harmless policy unusable; the grammar needs a rule for ops whose contract already implies `Forbid`.
4. Ownership-returning error vs `?`: `EagerFftInPlaceError` carries `Box<EagerTensor>` in `Rejected` but `Execution(Error)` has no owner
   (consumed). Inside `with_eager_session`, whose closure error must be `From<tenferro_ad::Error>`, `?` drops the owner
   (`From<EagerFftInPlaceError> for Error`, eager_in_place.rs:66). Recovering the owner requires matching before `?`. Fine, but easy to misuse.
5. The error type is FFT-specific. A shared ownership-returning error (generic over the owner) would be needed if other consuming ops appear.
6. Mislabel: both fft and ifft report op name `"fft_in_place"` in validation errors (eager_in_place.rs, `require_runtime_dtype("fft_in_place", ...)`,
   `validate_host_fft_read_input("fft_in_place", ...)`).
7. CPU-only: non-CPU runtimes are rejected at preparation time (eager_in_place.rs `in-place FFT requires a CPU eager runtime`).

## Surprises
- Negative axis (-1) works for the in-place path.
- Tracked rejection message comes from `prepare_eager_in_place_input` (crates/tenferro-ad/src/extension.rs:95-101) and is shared by all in-place
  extensions; it also rejects active capture, which the tests do not exercise.

## Not verified
- No-rollback contract after execution begins: no way found to provoke a post-start failure on the CPU engine with a valid compact C64 input;
  the `Execution` variant is not exercised.
- Active trace capture rejection; non-compact (strided view) rejection; sliced-allocation preservation (#2023); C32; ifft norm variants beyond Backward.
- Behavior on non-CPU engines.
