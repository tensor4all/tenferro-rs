# P6: `TraceContext` einsum contraction trees

Files: `src/p6_trace_einsum.rs`, `tests/p6_trace_einsum.rs`. Adapter over the unchanged traced API
(crates/tenferro-einsum/src/traced.rs, crates/tenferro-runtime/src/{trace.rs,traced.rs,graph/compiler.rs}).

## What was built

`TraceEinsum::trace_einsum_with(&TraceContext, inputs: &[impl Borrow<TracedTensor>], spec, &TraceEinsumOptions)
-> tenferro_runtime::Result<TracedTensor>`. It (1) rejects any input whose `context()` is not the receiver
(`same_context`) with `Error::Validation` (`InvalidArgument`, `inputs`), (2) maps inputs to `TraceValue`s, (3) clones the
`TraceContext` handle (it is an `Rc`) to satisfy `TraceContextEinsumExt`'s `&mut self`, dispatches to
`einsum_with` / `einsum_subscripts_with` / `einsum_notation_with` by `EinsumSpec` variant (the spec type from P2), (4)
turns the resulting `TraceValue` into a `TracedTensor` with the `#[doc(hidden)]` `TraceContext::derive_tensor`.
Einsum errors are mapped to `tenferro_runtime::Error` (the `Runtime` variant unwrapped, others wrapped via `Error::extension`).

Verified by tests (execution via `Runtime::builder` + CPU engine registration + `install_extension_module(extension_module::<CpuEngine>)` +
`Runtime::prepare` + `Runtime::run`, results compared against an independent 2x2 complex product reference):
- balanced binary tree of N = 8, 64, 512 complex 2x2 matrices: A (TraceValue + `einsum_subscripts_with` + `finish` +
  `compile_traced_graph`), B1 (`trace_einsum_with` + `compile_many`), B2 (`trace_einsum_with` + `finish` +
  `compile_traced_graph`) all give the reference numbers (rel. 1e-10);
- input order is creation order, not use order (`x1 * x0` with inputs created `x0, x1`);
- unused input is pruned by both `finish`+`compile_traced_graph` and `compile_many` (`input_count == 2`), and
  passing 3 tensors to the pruned program fails at prepare;
- output order follows the order given to `compile_many` / `finish`;
- foreign `TracedTensor` rejected (both as input and when the owner differs); spec forms (text, subscripts, ellipsis
  notation, index lists) work; bad specs, wrong arity, empty inputs, rank mismatch are errors.

## Findings

1. **The owner-receiver name collides with the existing trait.** `TraceContextEinsumExt` already defines `einsum` and
   `einsum_with` on `TraceContext` with `&mut self` and `&[TraceValue]` (traced.rs:59, 104, 149). The proposal's
   `trace.einsum_with(&[a, b], spec, &opts)` would be an ambiguous method call while both traits are in scope; the
   prototype therefore had to use `trace_einsum_with`. Landing the grammar means replacing the `TraceValue` trait, not
   adding beside it.
2. **`&mut self` is vestigial.** `TraceContext` is an `Rc<RefCell<..>>` handle (`input`, `finish`, `derive_tensor` take
   `&self`), yet `TraceContextEinsumExt` takes `&mut self`; the adapter clones the handle just to call it. An owner
   receiver in the grammar should be `&self`.
3. **There is no public way to turn a `TraceValue` back into a `TracedTensor`.** The only route is
   `TraceContext::derive_tensor`, `#[doc(hidden)]` (trace.rs:424). `TracedTensorEinsumExt` has only `tensordot`
   (traced.rs:340-370); every einsum node on the TracedTensor layer needs the hidden hook. Leaves are public
   (`input_concrete_shape`, `from_vec_col_major`), derived values are not.
4. **`&opts` does not fit the by-value `EinsumOptimize`.** `EinsumOptimize` is not `Clone`, and one of its variants
   holds a `ContractionTree`, which is not `Clone` either. A borrowed `&TraceEinsumOptions` therefore has to clone
   `Auto/Nested/Path` by hand and must reject `Tree` (tested, returns `Unsupported`). Either `EinsumOptimize` becomes
   `Clone` (needs `ContractionTree: Clone`) or the options must be passed by value.
5. **Foreign values are already rejected for `TraceValue`.** I expected a `TraceValue` from another context to alias
   silently; it does not: `ForeignValue` is returned both for same-numbered and out-of-range handles
   (`Extension { kind: Validation(InvalidArgument), source: ForeignValue }`). The new check on the TracedTensor path
   gives an earlier and clearer error (`input N belongs to a different trace context`) but is not closing a hole.
   The two layers return differently-shaped errors for the same mistake.
6. **Input-key mapping differs between the two compile entries.** `compile_many` fills `CompiledGraph::input_keys`
   (graph/compiler.rs:192-205, from `plain_snapshot_with_inputs`), so a `TracedTensor` leaf's `input_key()` maps to its
   compiled slot (`input_key_index`). `finish` + `compile_traced_graph` passes `Vec::new()` (compiler.rs:134-136):
   `input_keys()` is empty and `input_key_index` returns `None` for every key, so the TraceValue path loses the
   mapping and callers must track pruning themselves. Pruning itself is identical (both reduce `input_count` to the
   live inputs, in creation order). `input_keys`/`input_key_index` are `#[doc(hidden)]`. A caller who builds with
   `trace.input(..)`, leaves a handle unused and relies on positions gets a silent renumbering, only detected when
   the input count mismatches ("compiled graph expects 2 ordered inputs, got 3").
7. The yao-rs `execute_scoped_read_only` / `ScopedReadInputs` path is gone; the current execution API is
   `Runtime::prepare(&CompiledGraph, &[TensorRead], &[EngineTarget])` then `Runtime::run(&mut [&mut dyn ExecutionEngine], &Prepared, &[TensorRead])`,
   with the einsum extension module installed explicitly (`install_extension_module(extension_module::<CpuEngine>(runtime_engine_id()?))`)
   as the tests do (I did not test running without it). Not mentioned by the traced einsum docs I read.

## Not verified

- Concurrent / reentrant use (`ReentrantContextBorrow`) of the owner receiver.
- Symbolic-shape inputs (only concrete 2x2 shapes), `EinsumOptimize::Auto/Nested/Path` on the traced path (all trees here
  use `EinsumOptimize::False` as yao-rs does), ellipsis on symbolic dims.
- Wall-time differences below ~25%: single process, no isolation from concurrent builds; no confidence intervals.
- Allocation counts exclude the finish/compile phases (only the build phase is counted).
- Execution on any engine other than `CpuEngine::serial()`.
